## Overlap with other docs

- **`offline_guide.md`**: doc's own line 29 explicitly hands off `tuner.offline_tuner` and `sim/`'s modules to `offline_guide.md`. This is the doc drawing its own boundary correctly, not unplanned overlap — but the audit brief anticipated overlap in "tuner/ layout" description; I did not diff the two docs' text side by side. Worth a follow-up diff pass in `offline_guide.md`'s tuner/ layout section against this doc's tool table for near-duplicate prose (both likely list `tuner/checks/*` and `tuner/tools/*` file purposes).
- **CLAUDE.md's `sync_mpc_params.py` section**: as shown above, debugging_tools.md's section (lines 115-134) and CLAUDE.md's "Syncing MPC/NMPC params specifically" section describe the SAME script with the SAME scope/direction/safety claims, and they agree with each other and with the actual code. This is intentional, sanctioned duplication (CLAUDE.md is meant to summarize cross-cutting concerns, debugging_tools.md gives the full tool writeup) — not a contradiction, but a maintenance-burden overlap: a future change to the script's scope needs updating in **three** places (CLAUDE.md, debugging_tools.md, and any offline_guide.md mention).
- **`docs/reference/offline_live_parity.md`**: has the MORE ACCURATE and MORE DETAILED account of the steering_sysid/steering_step situation (explains WHY the files are gone: "upstream discarded them... before raising a PR"). debugging_tools.md's steering-harness section (161-200) should defer to/cite this doc directly rather than restating a now-stale version of the same fact.

This is a legitimate "how to produce the input this tool consumes" cross-reference, not overlapping content.

## Readability problems

- The doc is long (318 lines) but well-sectioned with one heading per tool/tool-family; this matches CLAUDE.md's "Writing style" bullet-and-table preference reasonably well.
- Some sections (live_viz.py's window-hiding bug writeup, lines 155-159; the layout='constrained' writeup, lines 159) read as changelog/incident narrative embedded in a tool-usage doc — CLAUDE.md's own code-comment rule ("no dates, no changelog, no score history, those belong in docs/logs/") arguably applies to prose narrative in docs/*.md too per the "Writing style" section's general spirit, though that section is written primarily about docs/logs/*.md and code comments, not explicitly this catalog doc. These sections explain a past bug and its fix in first-person-adjacent narrative style ("Previously, a panel's y-axis category list was built by...", "Measured directly against a screenshot showing exactly that") rather than doc_lint.py's and CLAUDE.md's stated preference for present-tense, non-narrative statements of current system properties. This is borderline: the content itself is useful (explains WHY a design choice was made, satisfying the "mechanism without WHY" check below), but the voice drifts toward the "as we found" / incident-log style CLAUDE.md's writing-style section discourages for docs/logs/*.md — not clearly in scope for this catalog doc, but worth flagging.
- Line 27's table cell "After a param change is live-tested and confirmed good, is fsae_autonomous... still running the OLD weights?" duplicates almost verbatim into the section header at line 115-117. Minor redundancy, not wrong.
