# The story of the last three days of changes (2026-08-04 to 2026-08-07)

This document explains, in plain language and in the order it actually happened, everything that changed in this repo (`fsae_MPCTest`, the offline driving simulator/tuner) over the 61 commits made between `41309fc` (2026-08-04 17:14) and `3b1bedd` (2026-08-07 16:35). There is a five-day gap before `41309fc` (the previous commit is from 2026-07-30), which is why this document starts there — that gap marks the start of this particular run of work.

You do not need to know how to code to follow this. Every section explains: what problem we were looking at, what we changed, what we found out, whether it actually fixed the problem, and why that pushed us to try the next thing. Some sections end with "this turned out to be wrong" — that is not a failure, it is how this kind of investigation works. Several early guesses looked very convincing and were still wrong, and the document says so plainly each time, because pretending otherwise would make the story misleading to read later.

Background you need before any of this makes sense: this project has two copies of the same self-driving controller. One copy (`fsae_planning`, a separate repository) runs on the actual car, in a real physics simulator called FSDS, or eventually on a real car. The other copy lives in this repository and is a much faster, simplified stand-in for FSDS, used to try out hundreds of different settings quickly without needing the real simulator running. The whole point of this repository is that whatever we tune here should also work on the real car. Most of this document is the story of discovering that the two didn't quite agree, and slowly figuring out why.

## Part 1 — Getting the toolbox back in working order (the first few hours)

The very first commits in this run were not about tuning anything. They were about fixing the tools so that testing could even happen. The previous long stretch of work had left the offline copy of the planning code out of date compared to the real car's code, using topic names and structures that no longer existed. The first commit resynced this offline copy to match the real one, and rewrote the piece of code that connects them so it talks to the current version of everything. As part of this, a feature was added to load a real recording of a lap — actual cone positions seen by a real run — into the offline simulator, so it could be tested against a real track layout instead of only made-up test tracks. This recorded lap becomes hugely important for the rest of the story: nearly everything from here on is checked against this one recorded lap, because it is the closest thing available to "the real car's experience" without needing the real simulator running every time.

Right after that, the staging folder that gets used to prepare changes for review (a folder called `fsds_simulator`) was reorganised so its folder structure exactly matches the real repository's structure, file for file. This sounds boring, but it matters a lot later: multiple times in this story, a fix is made in one place and forgotten in the other, and having matching folder structures is what makes it possible to catch that.

A few small but necessary fixes followed: a broken example command in the documentation, a missing software dependency that would crash the controller on startup, and better instructions for how to actually launch things. None of these changed how the car drives; they just made sure people could run the software at all.

**Then, a real recorded lap of a competition test track was added** to use for testing. But loading it exposed that the tool for turning a lap's worth of raw cone dots into a smooth, drivable line down the middle of the track was buggy in several ways, one on top of another:

1. It sometimes cut the track's centre-line across itself where the lap crosses its own path (a figure-eight shaped test track does this).
2. Fixing that then caused the tool to take a wrong turn at that same crossing and jump to the wrong side of the track.
3. It also sometimes reconstructed the lap running backwards.
4. And on tight hairpin turns, the tool would wrongly think the lap had already looped back to the start, and cut the reconstruction short.

Each of these four problems was found and fixed one at a time — the first fix exposed the second problem, which exposed the third, and so on. This is a common pattern in this whole document: fixing one bug often reveals the next one hiding behind it, because you can only see a problem once you've gotten past the ones in front of it. By the end of this chain, the tool could reliably turn a messy real recording into a clean, correct lap to test against.

With a working recorded lap, the offline simulator's assumption that the car's position is known instantly, with zero delay, was tested by adding a small delay on purpose (matching the tiny delay a real control loop actually has). This immediately triggered a known, pre-existing weakness: the offline simulator would swing wildly and sometimes crash off the track whenever any delay was simulated, because the steering decisions were being made based on stale information about where the car used to be. A fix was added: the controller now works out how old its positional information is, and mentally "fast-forwards" its guess of where the car actually is by that same tiny amount before deciding what to do. If there is no delay, this fast-forwarding step does nothing at all — checked and confirmed. With delay, it stopped the wild swinging. This same idea was later copied over to the real car's code too, since the same problem applies there.

Alongside all this, some behind-the-scenes improvements were made to the tuning software: an optional faster warm-up search step was added to help the main tuning process start from a better guess instead of a random one, and the tuning history log was made to record more detail about each run (like which scoring rules were active), so that later people looking back wouldn't misread old results using the wrong rulebook. A large, friendlier documentation page explaining the whole project was also written and cleaned up around this time.

## Part 2 — The first sign of trouble: steering wobble

With the tools working, attention turned to actual driving quality, and a real recorded log from a live run showed the steering wobbling — flipping left-right rapidly, worst in corners, sometimes badly enough that the car ran off track. Looking at the numbers driving this behaviour, the "cost" the tuning process placed on a wobbling steering wheel was about 40-60 times smaller than the cost it placed on other things like staying on the racing line. In plain terms: the tuning process had almost no reason not to let the steering wobble, because wobbling barely hurt its score. This was fixed by raising that cost significantly, and by separately making sure the tuning process reduces (rather than removes) its patience for a jittery correction while cornering hard, since a related setting had been letting the car "relax" its wobble-cost specifically in corners — exactly where the wobble was worst. A new, better way of even measuring "how wobbly was the steering" was introduced too, since the old measurement only counted how many times the steering flipped direction, without caring whether each flip was a tiny wiggle or a huge swing.

This was explicitly treated as a first, manual correction — a "let's stop the bleeding" fix rather than the final answer — and a fresh automatic tuning run was then done using the corrected scoring, which did produce an improved result by its own new scorecard. But — and this is the first big example of the story's theme — **this was not actually the real fix**. The wobble came back later and was eventually traced to a completely different and deeper cause several steps later in this story (see Part 3). The lesson here, stated plainly: a symptom (wobbly steering) can have more than one contributing cause, and fixing the first plausible-looking one doesn't mean you're done.

While validating this change, the staging mirror was expanded from covering just the control software to mirroring the entire software stack used on the real car, so that anyone could check out this repository plus the real simulator and run the whole thing without needing a second, separate checkout of the car's code. This is purely a convenience/organisation change, not a driving-behaviour change.

## Part 3 — Finding the real cause of the steering wobble

This is the first pivotal moment in the story. A fresh recorded log showed something very telling: the steering command was pinned at its absolute maximum allowed rate of change for 41 out of every 100 control decisions, and it was flipping direction roughly 8 times a second — while the car's actual position on the track stayed close to where it should be. In plain terms: **the steering wheel was hitting a speed limiter and bouncing off it, over and over, even though the car wasn't actually struggling to stay on the road.** That is not a "the settings are wrong" problem — no amount of retuning weights can fix a hardware speed limit being set wrong. And that's exactly what had happened: the tuning software's internal copy of the car had no such speed limit at all, so it had been tuned as if the steering could move as fast as it liked, while the real car's steering can only turn so fast per second. By working backwards from how fast the real car's cornering behaviour actually changed in the recorded logs, an estimate of the true steering speed limit was made, and the offline tuner's limit was corrected to match, while also adding the same real-world limit into the internal copy the tuning software optimises against, so future tuning results can't cheat this limit either.

While digging through the same logs to work all this out, a second, completely separate bug was discovered almost by accident: the number being logged as "steering angle in degrees" for one of the two controller types was actually being fed the wrong kind of number in the first place — a scale mismatch that inflated the logged steering values by roughly 2.3 times their true size. This had nothing to do with how the car actually drove, but it had been quietly hiding the speed-limiter problem above from view for an entire round of tuning, because the logged numbers looked plausible even though they weren't real. This was fixed, and the logging was made much richer and clearly labelled with units going forward, specifically so a mistake like this would be obvious next time rather than hidden.

Fixing the speed limiter was a real, measured fix for a real, measured bug. But the commit that made this fix was honest about a limitation found at the same time: even with this fixed, the offline simulator was still only wobbling a tiny fraction as often as the real car — a handful of direction changes per run offline versus well over a thousand on the real car, on the same course. Something else was still different. The best guess at the time was that the real car's positioning system (which uses cameras) is noisier than the offline simulator's perfect, noise-free version of "where the car is." So a model of that camera noise was added to the offline simulator as an optional extra, to test the theory.

**That theory turned out to be wrong** — and this is stated directly and clearly in the very next commit's own notes, correcting the previous one's implied guess. The recorded log being compared against was made entirely inside the same fast, simplified simulator being used for testing, and that simulator does not have a noisy camera model at all — it hands the controller perfect, ground-truth position information. So camera noise, whatever its real-world importance, could not have caused the wobble seen in that specific recording, because there was no camera noise in that recording to begin with. This is a good example of a hypothesis being reasonable to propose, cheap to test, and still simply incorrect — and the story says so rather than quietly moving on.

With camera noise ruled out for this particular problem, the actual answer turned out to be about *timing*, not *noise*. The part of the software responsible for reporting the car's position and the cones it sees was updating its output only 10 times a second, while the steering decision-maker runs 20 times a second — twice as fast. That means every second decision was being made using exactly the same, stale position information as the decision before it, because nothing new had arrived yet. Measured directly: over half of all steering decisions in the recorded log were working from a position that hadn't changed at all since the previous decision. The car doesn't stop moving just because the software hasn't reported it yet — it kept moving for that whole "frozen" period, and then the position information suddenly jumped to catch up all at once, causing an overcorrection. This is the classic shape of the wobble: freeze, drift a little unnoticed, catch up with a jolt, overcorrect, freeze again. The fix was to split this into two separate update schedules: position updates now happen at least as fast as the steering decisions need (20 times a second), while the slower, more expensive job of tracking cones can safely stay at its original, slower rate, since the cone map doesn't need to be refreshed as urgently as the car's own position does.

This is the fix that actually explains and resolves the specific wobble mechanism that had been chased since the start of Part 3. It stands in contrast to Part 2's earlier "cost function" fix, which helped a little but was addressing the wrong root cause.

## Part 4 — A second, unrelated failure: the car speeding into corners it can't make

With the timing bug fixed, a new problem showed up in a fresh test on the same recorded lap: the car drove fine for most of the lap, then failed completely partway through the second lap — swinging over 3 metres off the racing line and getting its steering pinned at full lock for half the lap. Investigating this showed the track's shape itself hadn't changed between the two laps — so it wasn't a mapping problem. It was a *speed* problem. The part of the software that decides how fast the car should be going only looks at the shape of the road ahead — it has no idea whether the car is actually on that road right now or not. So even while the car was already three metres off the racing line and at full steering lock trying to recover, this part of the software was still calmly telling it to speed up, because from the road's perspective, nothing looked wrong.

Several changes were made together to address this, and the reasoning for each is worth stating simply:
- The speed-planning software was made to look at several nearby measurements of "how curvy is the road here" and take a smoothed average, instead of trusting a single measurement that could be a fluke. A single bad reading had previously been able to set the speed target for an entire stretch of road.
- A brand new safety check was added: if the car is currently far off the racing line or pointing the wrong way, the target speed gets pulled down, roughly in proportion to how bad the situation is, with a floor so the car never gets told to fully stop. This stops the exact failure above — telling a car that's already in trouble to speed up.
- A limit was added on how fast the *target* speed is allowed to rise (braking is still allowed to happen instantly — only speeding-up is capped), which stops the target from jumping around frame to frame.
- A small mismatch was found and fixed where the two live-driving versions of the controller were looking at slightly different starting points along the road ahead of the car when judging the road's curviness, which the offline simulator was already doing correctly — so this was a real, if narrow, difference between how the offline and real versions behaved that needed to be brought back into line.

Tested on ten made-up test roads, the worst-case sideways error dropped from 1.76 metres to 0.79 metres, and a road that had previously caused a total failure in one mode no longer did. So, in the terms this whole document uses, yes, it worked, and it was measured to have worked.

However — and this is flagged explicitly rather than treated as a full solution — **this whole set of fixes is a safety net, not a repair.** The actual root problem behind why the road's shape sometimes looks "curvier" than it really is remained: the way raw cone sightings get turned into a smooth centre-line was occasionally producing physically-impossible kinks — implying a turn tighter than the track's tightest real corner — and this got worse the longer a lap went on, consistent with clutter building up in the memory of where cones are as more of them get spotted over time. This is called out here as a known, still-unfixed weak spot in the path-building software. Everything described in this section works around that weak spot rather than fixing it, and if that weak spot is ever properly fixed later, these safety nets should be re-checked rather than assumed to still be needed in their current form.

## Part 5 — Realising the scoring system itself couldn't tell good driving from bad driving

Separately from the driving-behaviour work above, a check was run comparing a handful of deliberately-crafted example "driving styles" — including one that deliberately wobbles the steering — against the single overall score number the tuning software uses to judge quality. **The deliberately bad, wobbly driving style scored better than the calm, sensible one.** That is about as bad a result as a scoring system can produce, because it means the automatic tuning process, left to its own devices, would be actively steered toward the wobbly behaviour rather than away from it.

The explanation was straightforward once looked into properly: the overall score is a sum of twelve different measurements, each with a "how much do we care about this" weight attached, but the twelve measurements are naturally very different sizes from each other — one might typically be a value around 0.007, another around 2.5. Multiplying a small weight by a naturally huge measurement can still swamp a large weight multiplied by a naturally tiny measurement. In the specific comparison run, essentially the entire score difference between the good and bad driving style came from just two of the twelve measurements, and the other ten combined barely moved the needle at all — including the "steering wobble" measurement specifically added a short time earlier in Part 2, which turned out to be so small in its natural scale that it was mathematically almost incapable of influencing the score at all, no matter what weight was put on it. This also explained, in hindsight, why an earlier attempt to discourage wobbling by hand-adjusting its weight (mentioned back in Part 2) barely did anything — the weight was being multiplied by a number too small to matter.

The fix was to divide each of the twelve measurements by a typical reference size for that measurement before applying its weight, so that all twelve are placed on a comparable footing before the weights are applied, rather than some naturally dwarfing others regardless of the weight chosen. After this fix, the wobble-related measurements became roughly ten times more influential on the final score than before.

This helped, but — again, stated plainly rather than glossed over — **it did not fully fix the problem.** Even after rebalancing the scale of each measurement, adding up twelve different, sometimes competing, priorities into one single number has a mathematical ceiling on how well it can express "actually, don't do that" for a bad style that happens to also be good at one or two of the twelve things. The next round of changes had to restructure the scoring system's actual shape, not just its dial settings, to get past that ceiling — described next in Part 5b.

## Part 5b — Rebuilding the scoring system properly, in tiers

A more thorough rebuild of the scoring system followed, addressing three related problems at once:

First, the part of the software estimating "how much should the car slow down for the corner ahead" only looked at the single sharpest curve visible within its lookahead window, with no sense of *how far away* that curve actually was. A hairpin bend far in the distance was treated exactly the same as one right in front of the car, which could ask the car to brake far harder than physically possible — the equivalent of demanding a passenger-car braking force several times beyond what any real car (or its tyres) can produce. This was fixed by making the speed target take distance into account properly: for each curve spotted ahead, work out the fastest speed the car could realistically be going right now and still be able to slow down in time for it, and let the most restrictive of those checks win. Measured on a simple test road (a straight leading into a tight hairpin), this dropped the demanded braking force from an unrealistic level down to a much more plausible one, and the car's overall test performance across ten roads improved.

Second, the reference used to judge "how good was your lap time" had been a rough placeholder guess since the very start of the project, and was found to be several times more generous than what the car could realistically ever achieve — meaning a "close to the theoretical best" score didn't mean very much. This was replaced with an actual physics-based calculation of the fastest a lap could genuinely be driven given real cornering and braking limits, checked against a simple straight-line case as a sanity test. Two smaller mistakes were caught and fixed while building this: the calculation had first used an overly cautious cornering limit (making the "theoretical best" time slower than what the car could actually beat in some test runs — an obvious sign something was wrong, since nothing should beat the theoretical best), and it hadn't accounted for laps that stop just slightly short of a full finish.

Third, and most fundamentally: adding up many different priorities into one weighted-sum score, even with well-balanced weights, mathematically cannot rule out every possible bad trade-off — a driving style can still "buy back" a genuine safety failure by being extremely good at some unrelated measurement. The scoring system was restructured into three separate tiers instead of one flat sum: a hard safety tier (crashing or going off-track is now penalised on its own separate scale, not something that can be offset by good numbers elsewhere), a lap-time tier (how close to the newly-calculated true best time the lap was), and a smaller "quality" tier (the twelve detailed measurements from before, now playing a supporting role rather than the whole picture). Retesting the earlier deliberately-wobbly-versus-sensible comparison from Part 5 with this new structure reversed the previous wrong result: the sensible driving style now scored clearly better than the wobbly one, which is the correct outcome.

A short cleanup pass followed this, catching a few real gaps that a first round of "we checked this is correct" claims had actually missed: the on-screen graphical tool used for manually testing hadn't been updated to use the new lap-time calculation, so it was silently still using the old, overly generous placeholder — meaning a person testing by hand and the automatic tuner were being judged by two different rulebooks without realising it; the written documentation explaining the scoring system hadn't caught up with two rounds of changes and was actively describing an old scale as if it were current; and the staging mirror copy of one file hadn't received the corner-braking fix from earlier in this section. All three were fixed. This is another recurring theme worth naming directly: even a careful "I checked this" claim can miss things, and going back to actually re-verify is what catches that, rather than assuming a previous confidence was airtight.

With scoring now believed to be in a trustworthy state, a fresh automatic tuning run was done to find new settings under the corrected rules.

## Part 6 — The big question: why does the real car still drive worse than the offline simulator predicts, even with a "clean" score?

This is the heart of the whole investigation, and by far the largest section, because it involved testing and ruling out several plausible explanations one at a time before finding the real answer — and even the real answer only explained part of the gap.

The starting puzzle: with a freshly-tuned set of driving settings, the offline simulator predicted smooth, clean driving on the recorded test track. But when those exact same settings were used on the real car (in the full FSDS simulator, which is a much closer stand-in for a real car than this repository's simplified offline copy), the car wobbled and struggled on the very same track. Something about the offline simulator was too easy, too forgiving, compared to reality — but what?

**Attempt 1 — maybe the car's position updates sometimes freeze for longer, unpredictably, on the real system.** Two real recorded runs on the exact same track and settings were compared: a "smooth" run where the position updated reliably about 19 times a second with the longest freeze being a quarter of a second, and a "failed" run where the position only updated about 6 times a second, with one freeze lasting almost a full second — during which the car covered around 17 metres essentially blind, then spun out with a severe heading error once the position caught up. This matched the exact mechanism from Part 3, just worse and more variable in the real world than what had been assumed. A model of this kind of freezing was built into the offline simulator to test whether reproducing it would close the gap.

**It didn't.** This is stated directly: even with this freezing behaviour faithfully reproduced and confirmed to be firing at a realistic rate, the offline simulator's steering-lock-up rate barely moved (from about 3% to about 4% of the time), while the real car's was over 21% of the time — nowhere close. Several other quick checks were done in the same pass and also came up empty: grip levels looked similar between offline and real, the offline car wasn't actually approaching corners faster than the real one, the offline path-planning was if anything slightly *cleaner* than the real one (so that wasn't hiding a problem either), camera noise barely moved the numbers, and slowing down how often the path gets rebuilt actually made the offline result better, which was the wrong direction to explain a real-world problem. All of this narrowed things down by elimination, even though none of it was the answer.

**Attempt 2 — maybe the offline simulator's simulated tyre grip is set wrong.** An earlier, quick comparison (done as a side-check during attempt 1) had compared the *average* amount of sideways force in each version and found them similar, and had used that to wave grip away as a cause. **This was later re-examined and explicitly retracted as the wrong test** — an average tells you how hard the controller *chose* to corner, not what the car is actually *capable* of, so it can look similar even when the true capability is very different. Done properly this time: the real car's actual cornering-versus-steering-angle relationship was measured directly from real driving data and used to work out what tyre grip setting would be needed to match it. A specific number was found that matched this relationship almost exactly. But that same number, when checked against two other independent measurements — how the car behaves at full steering lock at low speed, and how often it actually locks up its steering in the closed-loop test — failed both checks badly. Trying other grip values nearby just traded one kind of failure for a different one (the car would instead slide off the road entirely). The real car was also observed holding full steering lock for sustained stretches of over a second at a time, at a force level well within what should be a safely achievable grip limit if grip were the actual constraint. **Conclusion: grip was ruled out.** Two independent ways of measuring "how much sideways force can this car generate" gave two different, inconsistent answers, which is the signature of the wrong kind of model being fitted, not a parameter that just needs adjusting. A standing note was added warning against trying to patch this problem by adjusting tyre-grip numbers again in future, since it had already been tried properly and failed.

**Attempt 3 — maybe the real car simply can't turn as sharply as commanded, at all speeds equally.** A dedicated measuring tool was built: instead of using the full driving software (which reacts constantly, making it impossible to isolate the car's raw physical behaviour from the controller's own choices), this tool sends a fixed steering command at a fixed speed with nothing else happening, and just records what actually happens to the car — removing the controller and its decisions entirely from the picture, leaving only the raw response of the vehicle itself. Before trusting a single number from that tool, it was tested against several fake, artificially-generated logs where the "true" cause was already known in advance, to make sure the tool's analysis method could correctly identify each of five different candidate explanations rather than guessing.

**Applying this tool to real driving logs first gave a useful clue, but also ruled out the previous leading suspect.** The measured pattern showed the car achieving less and less of its commanded steering angle as speed increased — not a constant, fixed shortfall regardless of speed, which is what would be expected if the issue were simply a wrongly-configured maximum-steering-angle number in the software (a hypothesis raised at the end of the grip investigation above). Since the shortfall changed with speed rather than staying constant, that specific suspect was ruled out too. A few other candidates were checked and also eliminated at this point: delay in the physical steering mechanism, a logging mistake, and an unrealistic front-versus-back tyre balance.

**Then the actual open-loop experiment — steering fixed, speed fixed, nothing else running — was performed properly, and this is the breakthrough finding of the whole document.** Below about 5 metres per second, the real car delivers essentially exactly the steering angle it's told to, matching the command almost perfectly. Above that speed, the car's actual turning response collapses sharply — not gradually — dropping to roughly a third of the commanded angle at a moderate speed, and down to around a sixth of it at higher speed. Comparing five different candidate explanations against this exact measured shape, one fit dramatically better than all the others: **the real racing simulator (FSDS) appears to enforce an invisible ceiling on how hard the car is allowed to corner, once it's going fast enough, that the offline simulator has no idea exists.** Crucially, this ceiling sits well below what the same car has been observed doing elsewhere at other times — so it isn't a case of "the tyres just can't do more," because a genuine grip limit wouldn't depend on speed the way this clearly does; it looks instead like a deliberate, speed-triggered safety behaviour built into the simulator itself.

This single finding explains the entire original problem end to end: the driving decision-maker plans a corner assuming the car can turn as commanded, the real simulator quietly refuses to let it turn that much, the car's heading drifts off from where it's supposed to be pointing, the decision-maker responds by demanding even more steering to correct the drift, and that demand runs straight into the car's hard steering-angle limit — which is exactly the "steering pinned at maximum" pattern that had been measured and chased since Part 3.

The exact nature of this hidden ceiling — is it a hard stop, a scaled-down response, or something that resists and settles over time — still wasn't known, since these different possibilities all produce the same measurements when the car is driving at a constant, unchanging condition and only look different for a brief moment right after a sudden steering change. A second, more targeted tool was built to apply a sudden, held steering change and watch exactly how the car responds in that first fraction of a second, sampled quickly enough to actually see the shape of that brief moment rather than blur it into a smooth-looking average.

Running that experiment gave two pieces of evidence together: yes, there is a genuine ceiling — pushing the steering much harder barely raised the eventual, settled turning result. But — and this is the detail that determines exactly what kind of ceiling it is — **the car briefly overshoots past the ceiling by around 30% before settling back down to it.** A simple hard stop cannot ever overshoot past itself, by definition, so this rules out the simplest possible explanation and instead points to something that behaves like a force building up gradually and pulling the car back once it exceeds a threshold, rather than instantly refusing to go further. The specific physical quantity being held near-constant was confirmed to be sideways (cornering) force rather than the plain rate of turning, and the ceiling was measured at roughly 7.5 units of sideways force — again, comfortably below what this same car is known to be able to produce, confirming this is a deliberately-imposed limit and not a hardware limit.

This mechanism was then built into the offline simulator, as a gradually-building restoring effect (not a hard clip, since a hard clip would remove exactly the "brief overshoot before settling" behaviour that had just been measured and confirmed as real). Building it required correctly fitting several numbers: how strong the ceiling's pull-back effect is, how quickly it kicks in, and the ceiling level itself.

**Getting these numbers right took two more rounds of correction, and the reasoning behind the correction is itself an important lesson.** The first attempt fit the strength of the ceiling to match the eventual, settled cornering force seen in the earlier measurement — but this made the ceiling behave almost like an absolute wall, and caused the car to spin off the track entirely during a full test lap, because real corners arrive faster than this overly-strong version could react to. Reducing the strength to instead match the observed brief overshoot peak (rather than the settled value) fixed the spin-off, but this created a subtly different problem: the *settled* value it now produced was noticeably higher than what had actually been measured. Rather than treating these as two separate, unrelated mistakes to patch individually, it was recognised that they were **two symptoms of one deeper structural flaw**: the mathematical style originally chosen to build this restoring effect can only ever produce output once there's already some error to react to, meaning its resting state, by the nature of how it's built, must always sit slightly past the true ceiling — no adjustment of its strength can ever fully fix that, because the flaw isn't in the numbers, it's in the shape of the underlying idea. Switching to a different mathematical style — one that keeps building up its pushback for as long as any excess remains, rather than needing an ongoing excess to produce any pushback at all — fixes this by construction: its resting value naturally settles exactly on the ceiling for any reasonable strength setting, leaving only the fitting of that one strength number, calibrated against the measured overshoot alone. Tested against a completely separate part of the earlier real-world measurements that had not been used to fit anything, the accuracy of this new version was about five times better than the old one.

Even with this fixed, though, **the steering-pinned-at-maximum problem was only partly closed, not solved.** With the corrected ceiling model, the offline simulator's own rate of hitting maximum steering only rose to a few percent, while the real car was still doing it about a fifth of the time. The last unmeasured piece — exactly how quickly this restoring pushback effect builds up — was measured properly with a longer, cleaner version of the sudden-steering-change test, giving a much more confident and consistent number than the very rough first guess. But testing this refined number showed **it moved the offline simulator's steering-lock-up rate in the wrong direction** — further from matching the real car, not closer. This was reported honestly as a real, if small, step backward on this one measurement, justified as still being the right thing to ship because it's a genuine, carefully-measured property of the simulator's real behaviour, not a dial meant to be tuned to make the gap look smaller — chasing a moving target by re-fitting a physical property to make one comparison look better would just be fooling the comparison, not fixing anything real.

At this point, with the ceiling's existence confirmed, its overall level confirmed, and its build-up speed now also carefully measured, and none of these three properly moving the remaining gap — a rigorous framework was finally built to answer a more basic question first: is any of this actually making a measurable difference at all, or is the "before versus after" comparison being used just noise from run to run? Testing every previously-tried adjustment repeatedly across several different test roads (rather than the single recorded lap used up to that point) showed that **every single one of these adjustments, individually, produced an effect smaller than the natural run-to-run variation of the test itself** — meaning none of them could be confidently said to have moved anything at all, even the earlier result that had looked like a step backward. Even generously adding together the two largest, non-overlapping effects only accounted for roughly a quarter of the total real-versus-offline gap that needed explaining. **At least three-quarters of the original gap remained completely unexplained by anything to do with this ceiling — its strength, its level, or its timing.** A useful additional clue came out of this same check: the ceiling's effect was concentrated almost entirely on certain types of turns and had essentially no measurable effect at all on others, which is a specific pattern that any future explanation of the remaining gap would need to also match.

This redirected the investigation away from the physical car model entirely, and back toward the *planned route itself* — specifically, an idea flagged earlier but not yet tested: does the planned path's intended heading swing around faster than any real or simulated car could ever actually turn to follow it, forcing a heading error that has nothing to do with grip, delay, or ceilings at all, and everything to do with the plan itself asking for something impossible?

Two specific, narrower versions of this idea were tested directly and mostly ruled out: one mechanism, where the path-planning software occasionally skips its normal smoothing step if the car has moved far enough since the last update, was confirmed to be a real behaviour that could in principle cause a big jump — but it was measured to happen precisely zero times across the entire recorded test lap being used for all these comparisons, so it couldn't be the explanation for what's happening on that specific lap, even though it remains a real risk worth keeping in mind on other track shapes. The general "does the everyday smoothing itself carry along noisy jumps from update to update" question was also checked directly and found to explain, at most, a very small sliver of the actual heading-error growth being chased — nowhere near enough to be the main story.

This process of elimination pointed back to the specific known planner weak-spot already flagged at the end of Part 4: physically-impossible sharp kinks occasionally appearing in the reconstructed centre-line. Investigating this properly identified a more precise root cause than had been assumed before — not built-up mess in the memory of cone positions over a long lap (the original guess from Part 4), but a much narrower issue in exactly how the very nearest, most recent stretch of road gets stitched onto the rest of the path at its edge. However, the very next check found that the way this problem's size had just been measured was itself flawed — it was mostly picking up completely ordinary, harmless resampling of points along the path, not the actual defect, wildly overstating how often the real problem occurs. Rebuilding the measurement properly and re-running it found the true rate of this specific defect to be extremely small — a tiny fraction of the earlier overstated figure — real, but far too rare on its own to explain the size of gap being chased. An explicit lesson was written down here, worth repeating plainly: a measurement that doesn't move after you fix its target isn't proof that your fix failed — it might mean the measurement itself was never actually tracking the right thing, and that possibility needs to be checked before concluding anything else.

Separately during this same stretch, while examining the cone-mapping code closely for unrelated reasons, **a genuine, previously-unnoticed bug was found and fixed**: when a brand-new cone is first spotted, and more than one nearby detection of that same physical cone arrives in the very same instant, the code had no way to notice that these were duplicates of each other (it only ever compared new detections against cones already firmly recorded, not against each other) — so both detections could become separate, permanent, never-merging duplicate entries for what is really one single cone. This was a real, confirmed, reproducible bug, and it was fixed properly across every copy of the code that has it. But — again reported honestly rather than oversold — testing this fix at realistic levels of camera imprecision did not measurably move the main steering-lock-up gap being chased at all, so while it's a genuine correctness fix worth having, it isn't the missing piece of this particular puzzle either. A separate, unrelated configuration mistake was also found and fixed around the same time: a file-ignoring rule had been accidentally written broadly enough that it was hiding an entire folder of legitimate mirrored files from version control, without anyone noticing, because the files were still present on disk and working correctly — just invisible to the tool used to check what had or hadn't been saved. This is exactly the kind of quiet, easy-to-miss trap that's worth knowing about even once fixed.

## Part 7 — Getting back to testing on the real thing, and a lesson about not trusting a single test run

With several offline leads now exhausted, actually running fresh tests on the real simulator became the priority again — but doing so was blocked by two small, unrelated technical problems that had crept in: a scripting mistake meant a startup script wasn't actually running the way it was supposed to, which broke a readiness check every time, and a networking quirk specific to running the simulator across two different operating systems side-by-side meant the two pieces of software simply couldn't find each other over the network without an extra setting being provided. Both were already fixed in one copy of the launch scripts and just needed to be copied over to the staging mirror copy as well. Fixing these unblocked the first fresh, real test run of this entire investigation — everything analysed before this point had relied on logs recorded earlier; from here on, new real tests could actually be run on demand again.

A first real test run, made with a batch of several accumulated live-side changes all applied together at once, showed the steering-lock-up rate improving from the original 21% down to about 15%. This looked like real progress. But it came with an important, clearly stated warning attached immediately: because so many different changes had all been bundled into this one test run together, there was no way to say which specific change (if any single one) actually caused the improvement, or whether it was some combination, or partly chance. Around the same time, some background research was done into the actual simulator software itself, looking for any public documentation that might directly confirm what kind of mechanism produces the steering ceiling found earlier. No definitive proof was found, but a specific, plausible, documented feature of the underlying game engine was identified that matches the measured pattern closely — full steering below a certain speed, reduced steering above it — though confirming it for certain would need access to internal data files that weren't available in a readable form.

Follow-up work then tried to untangle exactly which of the many bundled changes from that first promising test had actually caused the improvement. Reverting just one specific piece (a particular retuning of the driving-decision weights) back to an older version actually made the steering-lock-up measurement *worse*, which at least ruled out that one specific piece as the explanation — the improvement wasn't coming from that. The next most likely remaining candidate, by simple timing of when things changed, was the earlier position-update-speed fix from Part 3, but there was no easy way to isolate it further without more dedicated testing.

**And then, testing that specific remaining candidate on its own, directly, produced a genuinely useful and clear result:** deliberately reintroducing the old, slower position-update bug (from Part 3) into a fresh live test made things measurably worse — the steering-lock-up rate rose to about 32%, worse than both the earlier hopeful 15% test and even the very first 21% baseline this whole investigation started from. This directly confirms, for the first time by literally reproducing it and watching it happen live rather than only inferring it from old logs, the exact mechanism chased since Part 3: the car ran visibly off the intended path for close to a full second, its steering pinned hard against its physical limit the entire time, before slowly correcting itself back — precisely the "frozen position, drift unnoticed, catch-up jolt" pattern described all the way back then, now seen directly rather than only worked out statistically.

Finally, to check whether that earlier promising 15% result was a real, repeatable improvement or just one lucky run, a longer, five-lap test was done at the exact same settings that had produced it the first time. **The five-lap result was 26% — worse than both the original 21% baseline and the hopeful 15% single-lap result that had prompted this whole check.** Before accepting this number, a mistake in the analysis script itself was caught and fixed: it had been counting one very short section of track, created by the lap-counter accidentally re-triggering where the figure-eight track crosses itself, as if it were an entire extra lap, which distorted the per-lap statistics — this was confirmed as an error by checking the actual distance covered, which was far too short to be a real lap, and corrected before trusting the final number.

**The honest conclusion drawn from this, and where the investigation stands as of the last commit in this range:** the earlier 15% figure does not hold up and should be treated as superseded — a single run's number is not something that can be trusted on its own, however good a story it seems to fit at the time. The real, repeated picture is that the live car's steering-lock-up rate actually varies quite a lot from run to run under identical settings — somewhere in the range of roughly 15% to 32% — while the offline simulator, under its equivalent settings, consistently sits around 5%. So there is still a real, large, and now more honestly-characterised gap between offline predictions and real driving, but pinning down its exact size needs several repeated real test runs rather than trusting any single one, exactly the same discipline that had already been adopted for offline testing earlier in this story (Part 6) and is now recognised as equally necessary for live testing too. Two things from this stretch remain solid despite this final correction: the earlier finding that the retuned driving-decision weights were not the explanation for the 15% figure still holds regardless of which baseline number is used, and the underlying position-update-freezing mechanism itself remains directly confirmed and visible in the raw recorded data, independent of exactly what percentage it gets compared against.

## What this all adds up to, in one paragraph

Over three days, this investigation started from "the steering wobbles and the real car doesn't drive like the offline predictions say it should," fixed a real chain of tool bugs that were blocking any of this from even being testable, found and fixed a genuine timing bug that explained the original wobble, discovered the scoring system used to judge "good driving" was mathematically almost blind to the exact problem being chased and fixed that too, ruled out several very plausible-sounding explanations for the deeper real-versus-simulated driving gap (positioning noise, positioning freezes at a normal rate, tyre grip, a fixed steering-angle miscalibration), discovered a genuinely surprising and previously-unknown fact about how the real simulator behaves (a hidden, speed-triggered ceiling on cornering force that isn't a grip limit), modelled that ceiling correctly only after two rounds of getting the fitting approach wrong for structural, not just numerical, reasons, and then discovered through careful, repeated live testing that even accounting for all of this, roughly three-quarters of the real-versus-offline gap is still unexplained, and that a "promising" 15% result from a single test run did not survive being repeated. Nothing here was faked or overstated to make the story look cleaner than it was — several honest dead ends and one full retraction are included on purpose, because knowing what was tried and ruled out is exactly as valuable as knowing what worked, and is the whole reason this document exists.
