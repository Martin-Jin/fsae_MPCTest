# The story of the last three days of changes (2026-08-04 to 2026-08-07)

This document explains, in plain language and in the order it actually happened, everything that changed in this repo (`fsae_MPCTest`, the offline driving simulator/tuner) over the 61 commits made between `41309fc` (2026-08-04 17:14) and `3b1bedd` (2026-08-07 16:35). There is a five-day gap before `41309fc` (the previous commit is from 2026-07-30), which is why this document starts there — that gap marks the start of this particular run of work.

You do not need to know how to code to follow this. Every section opens with a few bullet points naming the specific problem, the specific fix, and the specific result, then a short paragraph filling in the reasoning for anyone who wants it. Some sections end with "this turned out to be wrong" — that is not a failure, it is how this kind of investigation works. Several early guesses looked very convincing and were still wrong, and the document says so plainly each time, because pretending otherwise would make the story misleading to read later.

Background you need before any of this makes sense: this project has two copies of the same self-driving controller. One copy (`fsae_planning`, a separate repository) runs on the actual car, in a real physics simulator called FSDS, or eventually on a real car. The other copy lives in this repository and is a much faster, simplified stand-in for FSDS, used to try out hundreds of different settings quickly without needing the real simulator running. The whole point of this repository is that whatever we tune here should also work on the real car. Most of this document is the story of discovering that the two didn't quite agree, and slowly figuring out why.

## Part 1 — Getting the toolbox back in working order (the first few hours)

- Resynced the offline copy of the planning code, which had gone stale against the real car's code (old topic names, old structures), and rewrote the connecting piece so it talks to the current version of everything.
- Added the ability to load a real recorded lap (actual cone positions from an actual run) into the offline simulator, instead of only artificial test tracks. This recording becomes the main thing almost everything else in this document gets checked against.
- Reorganised the staging folder (`fsds_simulator`) so its structure exactly matches the real repository's, file for file — this is what later makes it possible to notice when a fix lands in one copy and gets forgotten in the other.
- Fixed a broken example command in the docs, a missing dependency that crashed the controller on startup, and unclear launch instructions.
- Loading the newly-recorded lap exposed five separate bugs, one after another, in the tool that turns raw cone dots into a smooth, drivable centreline: it cut across itself at track crossings, then (after that fix) took a wrong turn at the same crossing, sometimes reconstructed the lap backwards, and on tight hairpins wrongly decided the lap had already finished. Each was found and fixed in turn — fixing one exposed the next.
- Added a small delay to the offline simulator's assumption of instant, zero-lag car position (matching a real control loop's tiny real delay). This immediately caused wild swinging/off-track crashes. Fixed by having the controller estimate how stale its position data is and mentally fast-forward its guess of where the car actually is by that amount. Confirmed it does nothing when there's no delay, and stops the swinging when there is. The same fix was later copied to the real car's code too.
- Added a faster warm-up search step to the tuning software, and made its history log record which scoring rules were active for each run, so old and new results can't get compared under the wrong rulebook by mistake.

The very first commits in this run were not about tuning anything — they were about fixing the tools so that testing could even happen. With a working recorded lap and delay handling in place, the project finally had a realistic, repeatable test to check every later change against.

## Part 2 — The first sign of trouble: steering wobble

- A real recorded log showed the steering wobbling — flipping left-right rapidly, worst in corners, sometimes badly enough to run the car off track.
- Found the scoring math barely punished this: the cost placed on a wobbling steering wheel was about 40-60 times smaller than the cost placed on staying on the racing line, so the tuning process had almost no reason to avoid it.
- Fixed by raising that cost significantly, and by stopping a separate setting from letting the car "relax" its wobble-cost specifically in hard corners — exactly where the wobble was worst.
- Replaced the wobble measurement itself: the old version only counted how many times the steering direction reversed, so a barely-perceptible wiggle counted exactly the same as a violent, full-lock swing. The new version instead adds up how large each reversal actually was (the total steering-angle swing across the reversal), so a big swing now counts far more than a small one, which is what lets the tuning process actually tell the two apart and penalise the violent kind.
- Re-tuned with the corrected scoring and got an improved result — by its own new scorecard.
- Expanded the staging mirror from just the control software to the entire real software stack, so this repo alone (plus the real simulator) is enough to run everything, without a second checkout of the car's code.

**This was not the real fix.** This section's changes were explicitly a "stop the bleeding" first pass. The wobble came back later and was traced to a completely different, deeper cause in Part 3. A symptom can have more than one contributing cause — fixing the first plausible one doesn't mean the job is done.

## Part 3 — Finding the real cause of the steering wobble

- A fresh log showed the steering command pinned at its maximum allowed rate of change 41% of the time, flipping direction roughly 8 times a second — while the car's actual track position stayed close to where it should be. This is a speed-limiter problem, not a settings problem: no amount of retuning weights fixes a wrongly-configured hardware speed limit.
- Root cause: the offline tuner's internal copy of the car had no steering-speed limit at all, so every setting tuned in it had been tuned against a car that could steer unrealistically fast. Estimated the real car's true steering-speed limit from how fast its cornering behaviour actually changes in the logs, and added that same limit to both the tuner's internal model and its scoring, so future tuning can't cheat it either.
- Found, by accident while digging through the same logs, a second bug: the number logged as "steering angle in degrees" for one of the two controller types was fed the wrong kind of number, inflating logged values by roughly 2.3x. This had quietly hidden the speed-limiter problem above for an entire round of testing, because the wrong-but-plausible-looking numbers never triggered suspicion. Fixed the conversion and made the logging richer and clearly labelled with units.
- Fixing the speed limiter was real, but even with it fixed the offline simulator was still wobbling only a tiny fraction as often as the real car (a handful of direction changes per run offline vs. well over a thousand on the real car, same course). Guessed the cause was noisier real-world camera-based positioning, and added an optional camera-noise model to the offline simulator to test that guess.
- **That guess was wrong.** The log being compared against had itself come from the same simplified simulator, which hands the controller perfect, noise-free position — so camera noise couldn't have caused the wobble in that specific recording, because there was no camera noise in it to begin with.
- Found the real answer: the part of the software reporting the car's position and cones was updating only 10 times a second, while the steering decision-maker runs 20 times a second — twice as fast. Over half of all steering decisions in the log were therefore working from position data that hadn't changed since the previous decision, because nothing new had arrived. The car keeps moving during that "frozen" gap, then the position jumps to catch up all at once, causing an overcorrection: freeze, drift, catch-up jolt, overcorrect, freeze again — the classic wobble shape.
- Fixed by splitting the update schedule in two: car position now updates at least as fast as steering decisions need (20 times a second), while the slower, more expensive cone-tracking stays at its original, slower rate.

This is the fix that actually explains and resolves the wobble chased since the start of Part 3, in contrast to Part 2's cost-function fix, which helped a little but was treating the wrong root cause.

## Part 4 — A second, unrelated failure: the car speeding into corners it can't make

- A fresh test on the same recorded lap: the car drove fine most of the lap, then failed completely partway through the second lap, swinging over 3 metres off the racing line with steering pinned at full lock for half the lap.
- The track's shape hadn't changed lap to lap, so it wasn't a mapping bug — it was a speed bug: the speed-planning software only looks at the road shape ahead and has no idea whether the car is currently on that road at all. Even while the car was already 3 metres off-line and at full steering lock trying to recover, this part of the software was still calmly telling it to speed up.
- Fixed with four changes together:
  - Smoothed the "how curvy is the road here" reading by averaging several nearby measurements instead of trusting one, so a single fluke reading can no longer set the speed target for a whole stretch of road.
  - Added a genuine safety check: if the car is far off the racing line or pointing the wrong way, pull the target speed down (in proportion to how bad it is, with a floor so it's never told to fully stop) — this directly stops the exact failure above.
  - Capped how fast the *target* speed is allowed to rise (braking can still happen instantly — only speeding up is capped), so the target can't jump around frame to frame.
  - Fixed a small mismatch where the two live-driving controller versions measured the road ahead from slightly different starting points than the offline simulator did — brought all three into line.
- Tested on ten made-up test roads: worst-case sideways error dropped from 1.76 m to 0.79 m, and a road that used to fail outright in one mode no longer did.

**This whole set of fixes is a safety net, not a repair.** The actual root problem — the centreline-building tool occasionally producing physically-impossible kinks tighter than the track's tightest real corner, apparently worsening as more cones accumulate over a lap — is still there and still unfixed. Everything in this section works around that weak spot rather than fixing it; if that weak spot is ever properly fixed, these safety nets should be re-checked, not assumed to still be needed as-is.

## Part 5 — Realising the scoring system itself couldn't tell good driving from bad driving

- Ran a check comparing a handful of deliberately-crafted "driving styles" — including one that deliberately wobbles — against the overall score. **The deliberately bad, wobbly style scored better than the calm, sensible one.** Left to its own devices, the automatic tuner would have been steered toward the wobbly behaviour, not away from it.
- Found why: the overall score adds up twelve different measurements with weights attached, but the twelve measurements are naturally very different sizes (one might typically be ~0.007, another ~2.5) — so a small weight on a naturally huge measurement can still swamp a large weight on a naturally tiny one. In the comparison run, essentially the entire score gap between the good and bad style came from just two of the twelve measurements; the other ten (including the wobble measurement added in Part 2) barely moved the score at all, regardless of weight. This also explains, in hindsight, why hand-adjusting the wobble weight back in Part 2 barely did anything.
- Fixed by dividing each of the twelve measurements by a typical reference size for that measurement before applying its weight, putting all twelve on comparable footing. This made the wobble-related measurements roughly ten times more influential.

**This helped, but did not fully fix the problem.** Adding up twelve competing priorities into one number has a mathematical ceiling on how well it can say "don't do that" to a style that's merely good at one or two of the twelve things. The next round of changes (Part 5b) had to change the scoring system's actual shape, not just its dial settings.

## Part 5b — Rebuilding the scoring system properly, in tiers

- **Fixed a braking-distance bug:** the "how much should the car slow down for the corner ahead" calculation only looked at the single sharpest curve visible, with no sense of how far away it was — treating a hairpin far in the distance the same as one right in front of the car, which could demand braking forces several times beyond what any real car can produce. Fixed by working out, for each curve ahead, the fastest speed the car could realistically be going and still slow down in time for it, then letting the most restrictive check win. On a straight-into-hairpin test road, this dropped the demanded braking force from unrealistic to plausible.
- **Replaced the "how good was your lap time" yardstick:** it had been a rough placeholder since the start of the project, several times more generous than the car could realistically ever achieve. Replaced it with an actual physics-based calculation of the fastest genuinely possible lap given real cornering/braking limits, checked against a simple straight-line sanity test. Caught and fixed two mistakes while building it: an overly cautious cornering limit that made the "theoretical best" slower than laps the car had actually beaten (a sign something was wrong), and a missing case for laps that stop just short of a full finish.
- **Restructured the score into three tiers** instead of one flat weighted sum, because a flat sum — even well-balanced — can always let a driving style "buy back" a genuine safety failure by being extremely good at something unrelated:
  1. Hard safety tier — crashing or going off-track, on its own scale, not offsettable by good numbers elsewhere.
  2. Lap-time tier — how close to the newly-calculated true best time.
  3. Quality tier — the twelve detailed measurements from before, now a smaller, supporting factor.
- Re-tested the wobbly-vs-sensible comparison from Part 5 under the new structure: the sensible style now scores clearly better than the wobbly one — the correct outcome.
- A follow-up cleanup pass caught three real gaps a first "we checked this" pass had missed: the on-screen manual-testing tool was still silently using the old, overly generous lap-time number; the written docs still described the old scoring scale; and the staging mirror hadn't received the corner-braking fix. All three fixed.

With scoring now believed trustworthy, a fresh automatic tuning run was done to find new settings under the corrected rules.

## Part 6 — The big question: why does the real car still drive worse than the offline simulator predicts, even with a "clean" score?

The starting puzzle: freshly-tuned settings drove smoothly in the offline simulator on the recorded test track, but the exact same settings made the real car (in FSDS, a much closer stand-in for a real car) wobble and struggle on the very same track. Something about the offline simulator was too forgiving compared to reality. This section is the largest in the document because it worked through several plausible explanations, one at a time, before finding the real answer — and even that answer only explained part of the gap.

**Attempt 1 — random position-update freezes, not just the steady 10Hz-vs-20Hz mismatch from Part 3.**
- Compared two real runs on the same track/settings: a smooth run (position updating ~19 times/second, longest freeze 0.25s) and a failed run (position updating only ~6 times/second, one freeze lasting almost a full second — the car covered ~17m essentially blind before spinning out once position caught up).
- Built a matching freeze model into the offline simulator to test whether reproducing this closes the gap.
- **It didn't.** Steering-lock-up barely moved (about 3%→4%), against the real car's over 21%. Several other quick checks in the same pass also came up empty: grip levels looked similar, the offline car wasn't approaching corners faster, the offline path was if anything cleaner, camera noise barely moved the numbers, and slowing the path-rebuild rate made the offline result *better* — the wrong direction to explain a real problem.

**Attempt 2 — tyre grip set wrong.**
- An earlier quick side-check (comparing *average* sideways force between offline and real) had waved grip away — **this was retracted as the wrong test**: an average measures what the controller chose to do, not what the car is actually capable of.
- Measured properly this time: fit a specific tyre-grip number to match the real car's actual cornering-vs-steering-angle relationship from real data. It matched that one relationship almost exactly — but failed two other independent checks badly (full-lock low-speed behaviour, and how often it actually locks up in the closed-loop test). Nearby grip values just traded one failure (this mismatch) for a different one (sliding off-road). The real car was also observed holding full lock for over a second at a force well within a safe grip limit.
- **Grip was ruled out.** Two independent ways of measuring the car's real cornering capability gave inconsistent answers — the signature of the wrong kind of model, not a parameter that just needs adjusting.

**Attempt 3 — the real car simply can't turn as sharply as commanded, uniformly.**
- Built a dedicated open-loop measuring tool: send a fixed steering command at a fixed speed with the driving software disconnected entirely, and record what actually happens — isolating the car's raw physical response from any controller decisions. Validated the tool's own analysis method first against fake logs with a known "true" cause, across five different candidate explanations, before trusting it on real data.
- First pass on real logs: the shortfall between commanded and achieved steering angle *grows with speed* rather than staying constant — ruling out a simple wrongly-configured maximum-steering-angle setting (a leftover suspect from the grip investigation). Also ruled out steering-mechanism delay, a logging mistake, and unrealistic front/rear tyre balance.
- **The actual open-loop experiment — steering fixed, speed fixed, nothing else running — is the breakthrough finding of this document.** Below ~5 m/s, the real car delivers essentially exactly the commanded steering angle. Above that speed, its actual turning response collapses sharply (not gradually) — down to roughly a third of the commanded angle at moderate speed, and around a sixth at higher speed. Comparing five candidate explanations against this exact shape, one fit dramatically better than the rest: **FSDS appears to enforce an invisible ceiling on how hard the car is allowed to corner, once fast enough, that the offline simulator has no idea exists.** This ceiling sits well below what the same car reaches elsewhere, so it isn't tyre grip — a real grip limit wouldn't depend on speed this way.
- This single finding explains the entire original wobble end to end: the software plans a corner assuming full commanded turning, FSDS quietly refuses to deliver it, heading drifts off, the software demands even more steering to correct, and that demand runs straight into the car's hard steering-angle limit — exactly the "pinned at maximum" pattern chased since Part 3.
- A second, faster test (a sudden, held steering step, sampled quickly) checked whether this ceiling is a hard stop, a scaled-down response, or something that resists and settles over time. Result: the car briefly **overshoots the ceiling by ~30% before settling back down to it** — a hard stop cannot overshoot itself by definition, so this rules out the simplest explanation and points instead to a force that builds up gradually and pulls the car back once a threshold is exceeded. Confirmed the quantity being held near-constant is sideways (cornering) force, not turning rate, with the ceiling measured at roughly 7.5 units of sideways force — again, comfortably below what this car is known to produce elsewhere, confirming a deliberately-imposed limit, not a hardware one.

**Modelling the ceiling took two rounds of correction, and the reasoning matters as much as the result:**
- First attempt fit the ceiling's strength to the *settled* cornering force from the measurement — this made it behave almost like an absolute wall and caused the car to spin off-track during a full test lap, because real corners arrive faster than this overly-strong version could react to.
- Fitting to the *overshoot peak* instead fixed the spin-off, but produced a *settled* value noticeably higher than what was actually measured. These two problems were recognised as **one deeper structural flaw, not two separate mistakes**: the underlying maths style chosen can only ever produce output once there's already error to react to, so its resting state must always sit slightly past the true ceiling — no amount of adjustment fixes that, because the flaw is in the shape of the idea, not the numbers.
- Switched to a different maths style that keeps building pushback for as long as any excess remains (rather than needing an ongoing excess to produce any pushback at all). This settles exactly on the ceiling for any reasonable strength setting by construction, leaving only one number (the strength, fitted from the overshoot alone) to tune. Tested against a separate, untouched slice of the real measurements: about five times more accurate than the old version.
- **Even with this fixed, the steering-pinned-at-maximum problem was only partly closed.** The offline lock-up rate rose to a few percent; the real car was still doing it about a fifth of the time. Measured the last unfitted number — how quickly the pushback builds up — properly this time (a longer, cleaner steering-step test), giving a much more confident number than the rough first guess. Testing it showed **it moved the offline lock-up rate the wrong way** — reported honestly as a small step backward on this one measurement, but kept anyway since it's a genuinely-measured real property, not a dial meant to make the comparison look better.
- Built a proper repeatability framework (testing every adjustment across several different test roads, not just the one recorded lap) to finally check whether any of this was moving anything at all, or just noise. Result: **every one of these adjustments — ceiling strength, level, and timing — individually produced an effect smaller than the natural run-to-run variation of the test itself.** Even generously combining the two largest, non-overlapping effects accounted for only about a quarter of the total gap. **At least three-quarters of the gap remained completely unexplained by anything to do with this ceiling.**

**Ruling out the path itself, mostly:**
- Redirected toward whether the planned route's intended heading swings faster than any car could ever follow, forcing heading error unrelated to grip/delay/ceiling.
- One specific mechanism (the path-planner occasionally skipping its normal smoothing step after a big jump) was confirmed real in principle but measured to happen **zero times** on the entire recorded lap used for every comparison in this document — not the explanation here. The general "does everyday smoothing itself carry noisy jumps" question was checked directly and found to explain, at most, a small sliver of the heading-error growth — nowhere near the main story.
- Traced this back to the already-flagged planner weak-spot from Part 4: physically-impossible sharp kinks in the reconstructed centreline. Found a more precise cause than assumed — not built-up mess in cone memory over a long lap (the Part 4 guess), but a narrow issue in exactly how the nearest, most recent stretch of road gets stitched onto the rest of the path. **The very next check found the way this had just been measured was itself flawed** — it was mostly picking up ordinary, harmless resampling, wildly overstating how often the real defect occurs. Re-measured properly: the true rate is a tiny fraction of the earlier figure — real, but far too rare on its own to explain the gap. Lesson: a measurement that doesn't move after a fix isn't proof the fix failed — check whether the measurement itself was tracking the right thing first.
- Separately, while examining cone-mapping code for unrelated reasons, found and fixed a genuine bug: a brand-new cone spotted twice in the same instant could become two permanent duplicate entries instead of one merged cone, since the code only ever compared new detections against already-firmly-recorded cones, never against each other in the same instant. Fixed everywhere this code exists. Tested at realistic camera-imprecision levels: did not measurably move the main steering-lock-up gap — a genuine correctness fix, not the missing piece of this specific puzzle.
- Also found and fixed an unrelated configuration mistake: a file-ignore rule written broadly enough that it was silently hiding an entire folder of legitimate mirrored files from version-control checks, without anyone noticing, because the files were still present and working on disk — just invisible to the tool used to check "what's changed."

## Part 7 — Getting back to testing on the real thing, and a lesson about not trusting a single test run

- Two small technical problems had been blocking every attempt to run a real live test this session: a scripting mistake meant a startup script wasn't actually running the way it was supposed to (breaking a readiness check every time), and a cross-platform networking quirk meant the two pieces of software running on different operating systems couldn't find each other without an extra setting. Both were already fixed in one copy of the launch scripts; copied the fix over to the staging mirror too. This unblocked the first fresh, real test run of the whole investigation.
- First real test, with several accumulated live-side changes bundled together: steering-lock-up improved from 21% to about 15%. Looked promising, but flagged immediately as **confounded** — with that many changes bundled at once, there was no way to say which one (or combination) actually caused the improvement.
- Alongside this, researched the underlying simulator engine's own public documentation looking for a known, off-the-shelf setting matching the measured ceiling behaviour (full steering below a speed threshold, reduced above it). Found a plausible, documented candidate feature, but couldn't confirm it directly — the relevant internal file wasn't readable in this session.
- Untangled the bundled 15% result: reverting one specific piece (a retuning of the driving-decision weights) made the lock-up measurement *worse*, ruling that piece out as the explanation. The next candidate by simple timing was the position-update-speed fix from Part 3.
- **Tested that specific candidate directly, by deliberately reintroducing the old bug**: made things measurably worse (lock-up rose to about 32%, worse than both the 15% and 21% baselines) — directly confirming, for the first time by literally reproducing it live rather than only inferring it from old logs, the exact mechanism chased since Part 3: the car ran visibly off the intended path for close to a full second, steering pinned hard, before slowly correcting — the "frozen position, drift, catch-up jolt" pattern, seen directly rather than only worked out statistically.
- Repeated the earlier "promising" 15% test five times at the exact same settings to check whether it was real or lucky. **The five-lap result was 26%** — worse than both the 21% baseline and the 15% single-lap result that prompted the check. Before trusting this number, caught and fixed a mistake in the analysis script itself: it had been counting one very short section (created by the lap-counter re-triggering where the figure-eight track crosses itself) as if it were an entire extra lap, distorting the per-lap statistics.

**The honest conclusion, and where this document ends:** the earlier 15% figure does not hold up and should be treated as superseded — a single run's number cannot be trusted on its own, however good a story it seems to fit. The real, repeated picture is that the live car's steering-lock-up rate varies quite a lot run to run under identical settings — roughly 15% to 32% — while the offline simulator, under equivalent settings, consistently sits around 5%. So a real, large gap remains, now more honestly characterised, but pinning down its exact size needs several repeated real runs, not any single one — the same discipline already adopted for offline testing in Part 6, now recognised as equally necessary live. Two things survive this correction regardless: the retuned weights are still not the explanation for the 15% figure, whichever baseline is used, and the position-update-freezing mechanism itself is still directly confirmed and visible in the raw data.

## What this all adds up to, in one paragraph

Over three days, this investigation started from "the steering wobbles and the real car doesn't drive like the offline predictions say it should," fixed a real chain of tool bugs that were blocking any of this from even being testable, found and fixed a genuine timing bug that explained the original wobble, discovered the scoring system used to judge "good driving" was mathematically almost blind to the exact problem being chased and fixed that too, ruled out several very plausible-sounding explanations for the deeper real-versus-simulated driving gap (positioning noise, positioning freezes at a normal rate, tyre grip, a fixed steering-angle miscalibration), discovered a genuinely surprising and previously-unknown fact about how the real simulator behaves (a hidden, speed-triggered ceiling on cornering force that isn't a grip limit), modelled that ceiling correctly only after two rounds of getting the fitting approach wrong for structural, not just numerical, reasons, and then discovered through careful, repeated live testing that even accounting for all of this, roughly three-quarters of the real-versus-offline gap is still unexplained, and that a "promising" 15% result from a single test run did not survive being repeated. Nothing here was faked or overstated to make the story look cleaner than it was — several honest dead ends and one full retraction are included on purpose, because knowing what was tried and ruled out is exactly as valuable as knowing what worked, and is the whole reason this document exists.
